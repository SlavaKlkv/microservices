# 0003. Идемпотентность: Postgres как истина, Redis как быстрый путь

Статус: принято

## Контекст

Outbox даёт at-least-once (ADR-0002), Kafka при перебалансировке группы
тоже переотправляет сообщения. Одно и то же событие придёт подписчику
несколько раз, и это нормальный режим работы, а не авария.

Дважды обработанное событие — это второе письмо пользователю, вторая
строка в истории и повторный переход статуса.

## Решение

Источник истины — таблица `processed_event` в Postgres. Вставка
`ON CONFLICT DO NOTHING` идёт **в той же транзакции**, что и бизнес-
запись: `rowcount == 0` означает дубль, работать не надо.

Redis добавлен только как быстрый путь перед Postgres: `SET NX EX` перед
обработкой. Если ключ уже занят — событие заведомо дубль, в базу можно
не ходить.

Отдельно: переходы саги идемпотентны сами по себе. Событие, пришедшее на
заказ, который уже в целевом статусе, — тихий no-op, а не 409. Ошибка
здесь заставила бы консьюмер гонять событие по кругу до DLQ.

## Последствия

Хорошо:

* «обработано» и «записано» не могут разъехаться: они коммитятся вместе;
* Redis снимает нагрузку с базы на очевидных дублях;
* любая неисправность Redis приводит к «обрабатывай через Postgres», а
  не к потере события. Недоступность Redis переводит консьюмер в
  деградированный режим, и он продолжает работать.

Плохо:

* заявку в Redis нужно снимать при падении обработчика — иначе повтор
  будет отброшен как дубль, а в Postgres записи так и не появится. Это
  сделано, и на это есть тест;
* `processed_event` растёт неограниченно, чистки пока нет.

Явно отвергнуто: делать Redis источником истины. Отметка «обработано»
обязана коммититься атомарно с бизнес-записью, а Redis в одной
транзакции с Postgres быть не может.
