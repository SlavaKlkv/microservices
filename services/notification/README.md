# notification

Делает свой шаг саги: получает `order.notify_requested`, пытается
отправить письмо и публикует результат обратно в шину.

## Роль в саге

```
order.notify_requested  →  письмо отправлено   →  order.notified
                        →  отправить не вышло  →  order.notification_failed
```

Запись уведомления и строка outbox с результатом появляются **в одной
транзакции**. Иначе возможен худший исход: письмо ушло, а сага об этом
не узнала и отменила заказ.

## Процессы

| Команда | Что делает |
|---|---|
| `uvicorn notification.main:app` | HTTP API (журнал уведомлений) |
| `python -m notification.consumer` | слушает `orders.events.v1` |
| `python -m notification.outbox_worker` | публикует результат в Kafka |

Консьюмер реагирует только на `order.notify_requested`, остальные
события саги ему не адресованы.

## API

| Метод | Путь | |
|---|---|---|
| GET | `/api/v1/notifications` | журнал с фильтрами по `order_id` и `saga_id` |

Плюс `/health`, `/ready` и `/metrics`.

## Отправка писем

Выключена по умолчанию (`NOTIFICATION_ENABLED=false`): иначе тесты и CI
ждали бы недоступный SMTP. В compose поднят mailhog — письма видно на
`:8025`.

`NOTIFICATION_FAIL_RATE` задаёт долю искусственных отказов. Значение
`1.0` — способ проверить компенсирующую ветку саги, не ломая SMTP.

Известное ограничение: письмо отправляется после коммита дедупликации,
то есть возможен сценарий «записали, но не отправили». Выбор осознанный
— лучше не отправить, чем отправить дважды.
